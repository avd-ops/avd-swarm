# Red team: avd-swarm spec and governance (2026-10-17)

Reviewed: [spec.md](spec.md) and [governance.md](governance.md) at the commit that adds this file. Each finding has a severity, what goes wrong, and the change to the spec. **Status** says whether the spec now reflects it.

Severity: **C** critical (a path to an unapproved write or a broken safety), **H** high (a guarantee the spec makes but can't keep), **M** medium (a gap that will cost a cycle), **L** low.

## Findings

| # | Sev | Finding | Change | Status |
|---|---|---|---|---|
| R1 | C | **A branch can run a modified workflow in `approve`.** The federated credential trusts the environment. If the environment allows any branch, someone who can push a branch, or an agent with repo write, can edit the workflow to do anything with the write token, and the approver sees a run, not the workflow diff. | `approve` and `resume` environments allow `main` only; the credential subject is `repo:<owner>/avd-swarm:environment:approve`; workflow files are protected paths with CODEOWNERS review. | Fixed in spec §5 |
| R2 | C | **The dispatcher chooses what runs.** Something must start the approve workflow, and if the plan travels as dispatch inputs, whoever holds the dispatch token picks the change. | The workflow takes only a plan ID. It reads the plan from the plan store, checks its hash and re-runs the gate. Only the `propose_change` function (its own identity) can write to the plan store; agents can't. The dispatch token is a GitHub App limited to `actions:write` on this repo. | Fixed in spec §5 |
| R3 | H | **Approving blind.** GitHub's approval screen shows a pending job, not the plan, so approvals become a habit. | A first job, without the environment, renders the plan into the run summary (targets, diff, blast radius, gate results, rollback). The approval job depends on it. avd-buddy links straight to that summary. | Fixed in spec §5 |
| R4 | H | **The chat can describe a plan differently from what it is.** If avd-buddy shows the agent's text about the plan, an injected or confused agent can misdescribe it. | avd-buddy renders plans only from the plan store, in a fixed layout, visually separate from agent text. Agent text never describes a plan's effect. | Fixed in spec §5 |
| R5 | H | **The kill switch's identity can escalate.** Managed Identity Contributor on the `approve` identity can also *add* a federated credential, and User Access Administrator can also *grant* roles. A compromised switch could open a write path. | Custom roles with delete-only actions: `federatedIdentityCredentials/delete` and `roleAssignments/delete`, scoped as narrowly as possible. The switch can only take capability away. | Fixed in governance §2.3 |
| R6 | H | **Resume is a standing escalation path.** `swarm-resume.yml` needs an identity that can recreate credentials and roles, which is exactly what an attacker wants. | Resume is a self-contained Cloud Shell block Nick runs as himself (lesson 0015), with no standing identity. The block clears the flag only after it verifies every layer is back. | Fixed in governance §2.3 |
| R7 | H | **"AVD-related objects only" can't be enforced with Graph application permissions.** `AuditLog.Read.All`, `Directory.Read.All` and `GroupMember.ReadWrite.All` are tenant-wide. The write identity could change any group. | Reads: the tool layer filters to registered groups, and the spec says plainly that the identity can read tenant-wide. Writes: put the AVD groups in an Entra administrative unit and give the `approve` identity Groups Administrator scoped to that unit only, with no tenant-wide Graph write permission. Never role-assignable groups. | Fixed in spec §6 |
| R8 | H | **A deployment plan is arbitrary code with broad rights.** The Deploy agent proposing deployments through `approve` would need Owner-level rights at subscription scope, far beyond the action catalog. | Deployments are never `approve` actions. The Deploy agent proposes a PR to avd-landing-zone's parameters, and that repo's own `deploy.yml` and environment run it. | Fixed in spec §4 |
| R9 | H | **Observers trust what avd-swarm tells them.** A compromised avd-swarm can sign false events. | Observers corroborate from Azure's own records: the Activity Log and Entra audit and sign-in logs for every swarm identity. The watchdog reads only those, never swarm events, for its `halt-all` triggers. | Fixed in governance §2.2 |
| R10 | H | **Static Web Apps Free can't enforce the sign-in the spec assumes.** Its preconfigured Entra provider accepts accounts from any tenant; on Free, routes can be limited only to invited roles. Restricting to your tenant, mapping a group, and putting Conditional Access on the app need a custom Entra app registration, which needs the Standard plan (verify against current docs before S1). | Standard plan, a custom Entra app registration for avd-buddy limited to the tenant, assignment required with one group, and Conditional Access requiring phishing-resistant MFA. | Fixed in spec §6 and §7 |
| R11 | M | **Poisoned eval cases are permanent.** Improve proposes eval cases from real conversations, and evals are append-only, so a crafted conversation could lock in wrong behavior as "expected". | Improve proposes the question; a person writes or confirms the expected answer before the case enters the set. | Fixed in spec §6b |
| R12 | M | **No tamper-evident audit trail.** Events go to observers, but avd-swarm keeps no record it can't edit. | Every event is also written to immutable blob storage (time-based retention, 1 year) that no swarm identity can delete. | Fixed in governance §2.2 |
| R13 | M | **The kill switch is never exercised.** A switch that has never tripped probably doesn't work. | A monthly drill in a test environment trips each position, checks every layer took effect, and resumes. A failed drill blocks S2+ deployments. | Fixed in governance §2.3 |
| R14 | M | **Token cost multiplies.** One question fans out to the coordinator and one or more specialists, all on Claude Opus 5.5, on a personally paid subscription. | The coordinator starts on a smaller model; specialists start on Opus 5.5 at their effort level; the daily token cap ships in S1, not S2. Measure cost per question from the first eval run. | Fixed in spec §4 and §9 |
| R15 | M | **A stolen avd-buddy session reads everything the agents can read.** It can't approve, because approval is a separate GitHub sign-in, but it can exfiltrate. | Conditional Access on avd-buddy (R10), short session lifetime, and `agents.activity` counters per operator so a read spike is visible to the watchdog. | Fixed in governance §2.4 |
| R16 | L | **Two kill switches with the brain can deadlock resume.** Each listens to the other. | A resume clears only its own switch; avd-swarm stays at `halt-actions` until the brain resumes too, and says so in avd-buddy. | Fixed in governance §3 |

## What held up
- No write token exists before a person approves, enforced by Azure, not by code.
- Agents hold no write tools; the worst a fooled agent can do is propose, and the gate and approval stand behind that.
- The observer never sees conversation text, so injected text can't reach it.
- The kill switch is outside the part it stops, and only takes capability away (after R5).

## Not resolved here
- **SQ1** (on-behalf-of identity in Foundry) changes R7's read story if it works.
- Claude models as Foundry *connected agents* and with function tools: to be confirmed against current docs before S1 (see the prior art review).
